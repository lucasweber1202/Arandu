# Instruções para agentes (Claude Code e similares)
- **Core estratégico v3.7 (§§39–44):** UMA plataforma para pequenas/médias/grandes empresas B2B via ofertas Essencial/Gestão/Enterprise; mesma segurança, autorizações, objetos, cálculos, API e histórico. Instituições são usuárias de portal de baixo atrito, NÃO rede obrigatória: buyer-first, resposta externa com autoria verdadeira, Central de Relacionamentos Financeiros por instituição/entidade e qualidade ponta a ponta. Este target-state é normativa de DIREÇÃO, não autorização para construir todos os módulos, criar forks, lançar tiers, integrar bancos, iniciar billing ou alterar produção. Leia `docs/ARANDU_SEGMENTED_PRODUCT_OPERATING_MODEL_V37.md` e `docs/ARANDU_V37_EVIDENCE_AND_DECISION_GATES.md`. Gestão como ICP inicial é hipótese; P0-A/P0-B de 29/10 prevalecem. Evitar métricas/claims comerciais sem teste com pessoas reais.

- **P0 de entrega decidido em 19/10/2026 (preservado na guideline v3.6 §37):** link público https://arandu-demo.vercel.app/ compartilhável, acessível e fiel ao produto atual da main aprovada, com limitações da simulação explícitas; em paralelo estação local com Demo real validada na máquina do owner. M3 hospedado continua separado e bloqueado até recovery/cutover. Ver docs/PUBLIC_DEMO_2026-10-29_PRIORITY.md. Não adicionar capacidades ao sandbox histórico nem chamar vitrine de backend pronto. Priorizar essas duas entregas antes de funcionalidades enterprise secundárias ou Production não crítica.
- **Sequência de produto e engenharia v3.6 (§38):** benchmark com evidências, adoção bilateral, primeiro valor e portal da instituição (P1-A), Demo M3 em trilha separada com recovery/cutover autorizado (P1-B), piloto validado, integrações e expansão condicionada. Plano operacional `docs/FINANCIAL_COMPETITIVE_EXECUTION_PLAN_2026-10-20.md`. Não deslocar esforços dos dois P0 de 29/10, não declarar metas de performance como SLA, nem pesquisa sintética como validação comercial.
- **Leia primeiro a diretriz mestra v3, a matriz viva e os boundaries.** Antes de planejar ou implementar qualquer alteração relevante, leia `docs/ARANDU_PRODUCT_ENGINEERING_GUIDELINES.md` (v3, autoridade estratégica), `docs/IMPLEMENTATION_MATRIX.md` (estado vivo e maturity state M0–M6 de cada capability) e `docs/FINANCIAL_PRODUCT_BOUNDARIES.md`. `docs/ARANDU_PRODUCT_ENGINEERING_GUIDELINES_V2_1_ADDENDUM.md` é histórico/superseded pela v3: serve de referência técnica para IDs `Add. X.Y` antigos e não prevalece sobre a v3. Documentos técnicos mais específicos regem a implementação concreta sem poder contradizer os limites e a direção de produto sem decisão explícita e atualização documental.
- **Maturidade não é sinônimo.** "Existe em código" (M1), "CI verde no HEAD exato" (M2), "hospedado" (M3), "validação de release" (M4), "produção" (M5) e "cliente" (M6) são estados diferentes (guideline v3 §5). Não eleve maturidade sem evidência do estado anterior nem por causa de blocker externo.
- **Não implemente a guideline inteira por inferência.** Requisitos `DEVE` de target-state governam como a capacidade será implementada quando chegar sua prioridade; não autorizam ampliar a missão da rodada, antecipar Product Packs, network/benchmark ou reconstruir módulos fora de escopo. Respeite missão explícita, dependências e roadmap antes de conveniência.
- **Preserve a tese B2B/enterprise e o moat de lifecycle.** O Arandu evolui como Financial Procurement Lifecycle OS / Financial Sourcing, Relationship, Contract, Governance and Lifecycle Infrastructure. RFQ/RFP e comparison são capabilities do core, não o moat isolado. Priorize Financial Graph, memória institucional, workflow recorrente, governança, provenance e integrações. Não abra frente consumer, não crie ERP/TMS genérico, não reconstrua terminal/OMS/EMS/execution venue quando integração especializada for adequada, não transforme o produto em banco/fintech transacional e não introduza recomendação automática de instituição sem revisão explícita da guideline.
- **Design é contrato (v3.3 §35).** Mudança de interface segue `docs/ARANDU_DESIGN_CONSTITUTION.md`: tokens únicos (tinta/petróleo), menu em cinco áreas com fonte única em `lib/finance/navigation.mjs`, nada de UUID/enum/função/ISO na tela, sem KPIs decorativos. `npm run check:design` falha se a identidade sair dos tokens; mudança visual relevante traz captura antes/depois (`npm run design:capture`, Demo canônica local).
- **Toolkit de UX/frontend para agentes.** Em toda tarefa visual, siga `docs/FRONTEND_AGENT_TOOLKIT.md` além da Design Constitution; Taste Skill, Web Design Guidelines, Awesome Design MD, Image to Code e Playwright CLI são ferramentas consultivas/opcionais, nunca exceções à identidade, segurança, testes ou governança. Não instale skills externos automaticamente nem substitua `@playwright/test`; se outro agente estiver tocando arquivos comuns, faça handoff sem conflito.
- **Legacy art marketplace is retired.** Do not reintroduce art-domain code, pages, assets, data, scripts, tests, routes, env vars or docs from Git history unless an explicit migration/recovery task authorizes it. `npm run check:legacy-art` (tree) e `check:financial-surface` (dist) falham se isso acontecer; contexto e ponte para o histórico em `docs/LEGACY_ART_RETIREMENT.md`.
- **Toda tabela nova nasce classificada.** Registre-a em `lib/finance/data-governance.mjs` (classificação, system of record, retenção, exclusão, export, hold); `scripts/test-finance-data-governance.mjs` falha se faltar. Ver `docs/FINANCIAL_DATA_GOVERNANCE.md`.
- **Financial Graph é conceito, não stack obrigatório.** Não introduza graph database, Neo4j, GraphQL, vector database ou nova camada de dados apenas por causa do nome `Financial Graph`; prove necessidade contra a arquitetura existente antes de adicionar tecnologia.
- **Decisão humana e proveniência são invariantes.** Não crie ranking default de provedores, “melhor proposta”, savings sem metodologia, dado financeiro inventado ou ação material tomada por IA. Pesos, critérios, aprovações e decisão pertencem ao cliente; cálculos e extrações precisam de fonte/premissas rastreáveis.
- **Enterprise foundations exigem operação real.** Mudanças que toquem dados, integrações, identidade, migrations ou produção devem avaliar, conforme aplicável, data minimization/retention, source of truth, idempotência/replay, degraded mode, auditabilidade, backup/restore, rollback, runbook, métricas e claims. Backup não equivale a restore comprovado; não alegue RPO/RTO, proteção de branch, certificação ou SLA sem evidência.
- **PRs exclusivamente documentais: um commit.** Reunir todas as mudanças na branch `docs/*`, conferir o conjunto antes de enviar e publicar **um único commit/push**. A política do `vercel.json` (`docs/VERCEL_PREVIEW_POLICY.md`) só publica automaticamente a `main`; nenhuma branch de trabalho gera preview. Não usar `docs/*` para código/UI: usar `feature/*`, `fix/*` ou `claude/*` e validar localmente. Os quatro checks do GitHub continuam obrigatórios e publicação de `main` não é desativada.
- **Push em lote.** Rode localmente `npm run check:all`, `npm run build` e os testes da área alterada (`npm run test:database` para SQL, `npm run test:e2e` para interface) e só então faça **um** push com os commits do lote. Nunca faça push commit a commit: cada push inicia quatro jobs pagos no GitHub Actions (ver `docs/GITHUB_ACTIONS_MINUTES.md` e `CONTRIBUTING.md`).
- Não faça push vazio nem feche/reabra PR para disparar o CI.
- Não desative checks, navegadores ou jobs, e não use `|| true` para ficar verde.
- Migration nova: arquivo aditivo em `docs/`, rollback em `docs/rollback/`, registro em `docs/supabase-migrations.json`, `scripts/check-migrations.mjs` e `scripts/test-database.sh`, teste em `tests/database/`.
- Branches: `main` é a **única** branch longa de produto. `feature/*` (e `fix/*`, `chore/*`, `docs/*`, `agent/*`, `claude/*`, `codex/*`) sai da ponta atual de `main` e volta para `main` por PR com os quatro gates verdes no HEAD exato; é temporária e apagada depois do merge. `pilot` está congelada (histórica) e não recebe PR. Demo e Production são os **dois ambientes permanentes** da mesma `main`. Pilot é etapa de validação; ARANDU_ENV=pilot permanece apenas para compatibilidade transitória até o cutover. A política única é `lib/runtime-mode.mjs`, com atribuições ativas e destinos separados em `lib/deployment-topology.mjs` — nunca por branch ou código divergente. Não use "merged" do GitHub como prova de integração: confirme com `git merge-base --is-ancestor <sha> origin/main` (a #135 foi mergeada em outra branch de feature). Ver `docs/FINANCIAL_DEPLOYMENT_WORKFLOW.md`.
- Ambientes permanentes: `ARANDU_ENV=demo|production npm run release:candidate:doctor`; Pilot é release validation stage, não terceiro Supabase. `pilot` continua aceito apenas durante a transição.
  Demo e Production nunca compartilham banco/Auth/Storage/segredos. Planejar a conversão de um ref não libera seed/reset: exige inventário, ausência de cliente/PII necessária, export e recovery. Diferença de comportamento entre ambientes (e-mail, webhooks, modelo externo, documentos reais, fixtures) só via `lib/runtime-mode.mjs`; não espalhe `if (demo)`.
- Não acrescente capability ao sandbox legado `/demo` (`finance/demo/`): a demo canônica é `ARANDU_ENV=demo` + `scripts/demo/seed.mjs` pela API real. Capability nova entra no seed da demo.
- Antes de considerar uma mudança pronta, aplique a Definition of Done e os gates da seção correspondente da guideline mestra v3 (§25.4, §26), incluindo testes negativos, cross-browser/mobile quando aplicável, ausência de overflow horizontal, documentação e evidência verificável.
